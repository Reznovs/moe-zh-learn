# 06 · 进阶篇：从 10M 爬到你算力天花板

> 目标：知道手里这 10M 的小模型只是一个"教学跑道"，
> 以及如果真要把它做大，规模、算力、数据、显存分别在哪儿卡住你。

|---|---|---|---|---|

## 2. 缩小到两条公式，你就能自己估算一切

```
训练计算量 ≈ 6 × 激活参数 × token 数          （算力账）
Chinchilla 经验：token 数 ≈ 20 × 激活参数      （喂饱模型的最低配比）
```

举例：激活参数 500M 的模型，最低要喂 20 × 500M = **10B token**；
每步算力 6 × 0.5B = 3G FLOPs/token，10B token ⇒ **约 3e19 FLOPs**。

把这套算法用在免费算力上（现实可用约 **1.1e20 FLOPs/月**，账见第 4 节）：

| 你想花的时间 | 总参数 | 激活参数 | 训练 token | 现实含义 |
|---|---|---|---|---|
| 1 分钟 | 11.9M | 5.6M | 0.007B | 就是现在的 L0 |
| 几小时 | 41.9M | 20.7M | 0.1–0.3B | L1，可以看专家分化 |
| **1–2 天** | 2–3B | 400–550M | 8–11B | 第一个"像样"的中文 MoE |
| 1 周 | ~2.5B | ~550M | ~11B | 同上，多跑点数据 |
| **1 个月** | 4–5B | ~1B | ~19B | 中国版 TinyStories 级：语言流畅、知识很薄 |
| 3 个月 | ~8B | ~1.7B | ~33B | 天花板前的最后一次扩容 |
| 6 个月 | ~10B | ~2.3B | ~47B | **显存路线的终点**，再加就没地方放优化器状态了 |

**两个必须理解的结论**

1. **限制你的不是"总参数多大"，而是"激活参数多少"**——因为它决定每个 token 要花多少算力。
   MoE 让你把总参数堆到激活参数的 4–5 倍，代价是显存。
2. **激活率的最佳区间是 15%–30%**。低于 10% 就要求你有几百 B token 才能喂饱每个专家，
   免费算力上属于自欺欺人。

## 3. 数据比算力更可能先卡死你

上表里 1 个月的方案需要 **19B token ≈ 20–40GB 纯文本**；半年方案要 **47B token ≈ 100–200GB**。
中文语料的现实情况：

- 高质量中文纯文本（清洗后）在开源世界里就那么多，删重、去广告、去乱码通常占掉项目**一半以上**的工作量；
- 从零造数据几乎不可能，只能拼：维基 + 网络小说 + 新闻 + 代码注释 + 自家文档；
- 每个来源都要做：编码统一、去模板化、段落切分、按 token 打包。

**实践建议**：先把"数据管线"做成一个能重复运行的脚本，语料按 **1GB 一个分片**存到云端，
训练时按分片流式读取。数据没有干净的分片化，训练就没法断点续训。

## 4. 免费算力的真实账（三个来源的实测/公开数据）

| 来源 | 硬性限制 | 现实可用算力 |
|---|---|---|
| Kaggle GPU | T4×2（2×16GB），30 小时/周，会话 ≤12 小时 | ≈ 0.9e19 FLOPs/月 |
| **Kaggle TPU v5e-8** | 20 小时/周，会话 ≤9 小时（断连是硬性的） | **≈ 1.5e20 FLOPs/月（主力，占 ~90%）** |
| Colab 免费 ×2 账号 | 无稳定配额，T4 不保证，12 小时上限 | ≈ 0.75e19 FLOPs/月 |
| 合计（理想 / 现实） | — | **≈ 1.6e20 / 现实约 1.1e20 FLOPs 每月** |

三条由此推出的操作原则：

1. **TPU 车道只跑训练**：v5e-8 是 8 块 16GB 芯片（不是一块 128GB），
   单张张量超过 16GB 就要切分，所以要写 JAX/PyTorch-XLA 的专家并行代码；
   训练脚本里那 15% 的调试时间会变成主要成本，所以先在本地方案上把逻辑调通。
2. **Colab 只做杂活**：它单卡算力只占总量约 5%，但非常适合跑评估、消融、数据分析、画图。
   注意两家服务条款都禁止"用多账号绕过资源限制"和"跑跨机分布式"，所以别把它当集群。
3. **云端存档救你的命**：把 checkpoint 每 20–30 分钟写进 GCS（保持桶在 us-central1，
   从 Kaggle/Colab 机器上传下载不计流量费，标准存储约 2–3 美元/100GB/月）。
   9 小时硬断线时你最多丢 2% 的进度，而不是整个训练。
   这也顺便解决了"Kaggle 笔记本输出只有 20GB"这个坎。

## 5. 真正的规模化技巧：稀疏上采样（upcycling）

**不要**从零训练大 MoE。正确做法是"先把稠密模型训好，再把最后几层改造成 MoE，继续训一点点"：

```
① 训一个稠密模型（比如 1.5B × 20–30B token）
② 只挑最后 1/3 的层（例如最后 8 层），把每层的 FFN 复制成 4 份
③ 复制时给每份加一点高斯噪声（σ ≈ 权重标准差的 1–10%）
   —— 不加噪声的话 4 个专家永远一模一样，门卫分不出谁是谁
④ 留一份"没被路由的"原始 FFN 当共享专家
⑤ 门卫初始化成接近 0（早期近似均匀分配），学习率重启到最后的 1/3–1/2，加几百步 warmup
⑥ 继续训 5–8B token，均衡损失系数取 0.01 左右
```

**为什么值得**：Google 的稀疏上采样论文里，
T5-Large 只多花 46% 训练时间就拿到 +1.5~2 个 SuperGLUE 分；
视觉模型 ViT-B/16 只多花 13% 时间拿到 +1% ImageNet（10-shot）。
同样的时间拿去继续训稠密模型，收益更低。

**什么时候才算成功**（验收标准，别自欺欺人）：

| 项 | 要求 |
|---|---|
| 对照组 | 必须同时训一个"同样 token 数的稠密续训"模型 |
| 成功 | 损失低于对照组，且 4 个专家的利用率都在 30%–70% 之间 |
| 失败 | 某个专家利用率 < 5%（塌缩），或损失高于对照组 |
| 回滚 | 丢掉 MoE 部分即可（原稠密权重还在），**成本为零** |
| 预算 | 至少准备 30% 额外算力，否则收益看不出来 |

现实中的层位置选择：DeepSeek-V3 明确保留了**前 3 层稠密**，其余才换 MoE（GLM-4.5 同样做法）；
Llama 4 Maverick 则是 MoE 层与稠密层隔层交替。原因见 `02-机制篇` 第 6 节。
最保守的起步做法是**只改造最后 1/3 层**。

## 6. 你会撞上的三堵墙（按撞墙顺序）

| 墙 | 表现 | 对策 |
|---|---|---|
| **数据墙**（最先撞） | 语料清洗、去重、打包吃掉一半以上时间，且 100GB 级文本很难一次备齐 | 分片 + 云端存储 + 流式读取；先做一个 5B token 的可用版本 |
| **存档墙** | 会话被踢、checkpoint 太大、上传太慢 | GCS/Drive 直传，20–30 分钟一存，只保留最近 3 个存档 + 每 N 步一个长期档 |
| **显存/生态墙**（最后撞） | 总参数堆到 ~10B 就再也放不下（优化器状态吃 3–4 倍） | 8-bit 优化器 / Adafactor + 梯度重算；或换 TPU 车道；到这就到顶了 |

---

## 7. 一句话总结这篇

> 算力不是你的天花板，**激活参数**和**数据量**才是：免费算力一个月能训 4–5B 总参数 / 1B 激活的中文 MoE；
> 想做更大的，正确路径是"稠密预训练 → 稀疏上采样最后 1/3 层"，而不是从零训大 MoE。
